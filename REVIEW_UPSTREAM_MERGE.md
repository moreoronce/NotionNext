#### B. `components/SEO.js` — heaviest conflict (15 conflict blocks)
Fork had rebuilt structured data as `@graph` (Organization/Person/WebSite/BreadcrumbList/BlogPosting/CollectionPage). Upstream used a simpler single-object form. **Decision: kept fork's `@graph` rebuild entirely**, but adopted upstream helpers:

- **Kept fork's async font loading** (CSS `media='print'` trick) over upstream's WebFontLoader — chose NOT to reintroduce the WebFontLoader `useEffect` that the fork had previously removed
- Merged upstream's `publishTime`/`modifiedTime`/`publishDay`/`lastEditedDay` fields into `getSEOMeta` (fork's `buildBlogPosting` needs `meta.publishDay`)

> **Review question**: The fork's `generateStructuredData` signature is `(meta, siteInfo, url, image, author, router)` — it takes `router` for route-based breadcrumb logic. Upstream's was `(..., siteUrl)`. Kept fork's `router` param. Is the `router`-based breadcrumb branching (lines ~370-435 of SEO.js) something you want to keep, or simplify?

#### C. `components/ExternalPlugins.js` — fork slim preserved
Fork had deliberately slimmed plugins (commit `e2b00633`). Merge re-introduced upstream's full plugin set (analytics, fireworks, sakura, music player, etc.). **Decision: kept fork's slim version**, but this left dead code: a `pluginsIdle`/`setPluginsIdle` `useEffect` referencing a removed `useState`. **Removed that dead block.**

> **Review concern**: When slimming, ensure no theme still references removed plugin exports. Verified `GlobalStyle` and `IconFont` are dynamically imported at file bottom (the fork moved them from top-level imports to `dynamic()`).

#### D. `components/Comment.js` — adopted upstream's expanded comment support
Upstream added Cusdis/Utterances/Gitalk/WebMention/Notion comments. Adopted the JSX blocks but the fork's file bottom was missing 4 `dynamic()` import definitions (Cusdis, Gitalk, Utterances, WebMention). **Restored all 4.** Verified each target component file exists.

*Note: `hexo` appears in both deleted and kept lists — verify intended.*

> **Review question**: Upstream's `opc` theme (new "personal company" theme) was adopted. Confirm this is wanted; it adds `themes/opc/{config,index}.js`.

#### F. `public/llms.txt` + `public/sitemap.xml` — removed

## Commit 2: `7a9a4825` — Runtime fix (caught by browser verification)

**File**: `themes/theme.js` (+16 lines)

**Bug**: `ReferenceError: getThemeExport is not defined` thrown at runtime when loading theme config.

**Root cause**: During merge resolution, I removed upstream's `getThemeExport` and `getFallbackThemeName` helper functions, judging them dead code (their sibling `scheduleFixThemeDOM` genuinely was — it depends on `domFixTimer`/`fixThemeDOM` which this fork doesn't have). But `importThemeConfig`, `importThemeLayout`, and `resolveThemeLayout` all call `getThemeExport`, and `resolveThemeLayout` calls `getFallbackThemeName`.

**Fix**: Restored both helpers. Did NOT restore `scheduleFixThemeDOM` (correctly absent — unused + broken deps).

**Why tests/build didn't catch it**: jest doesn't exercise `theme.js` dynamic theme loading; `next build` (SSG) uses the default theme at build time and doesn't hit the runtime `useCallback` path that dev SSR triggers.

> **Lesson**: `next build` passing ≠ runtime correctness. Browser smoke test on dev server was required to catch this.

## Commit 3: `00918f00` — FCP/LCP fix (caught by Lighthouse)

**File**: `conf/font.config.js` (1 line)

**Change**: `FONT_AWESOME` path `/vendor/fontawesome/css/all.min.css` (102KB) → `/css/all.min.css` (4KB)

**Root cause**: During merge, I adopted upstream's fontawesome path + the new `/vendor/fontawesome/` cache header in `next.config.js`. But the fork ships a curated 4KB fontawesome subset (`public/css/all.min.css`) covering only the icons themes actually use. The upstream full fontawesome 6.x is 102KB of render-blocking CSS.

**Measured impact** (Lighthouse mobile, 3-run median):
| Page | FCP/LCP before fix | after fix |
|------|--------------------|-----------|
| Homepage | 3.8s | 2.5s |
| Article | 4.6s | 3.4s |

> **Review question**: The `next.config.js` still has the `/vendor/fontawesome/:path*` cache header (adopted from upstream). It's now harmless (no requests hit it) but dead. Remove for cleanliness?

## Commit 4: `f5e22784` — TBT/Style&Layout fix (caught by Lighthouse + network analysis)

**File**: `lib/fonts.js` (16 insertions, 13 deletions)

**Change**: Removed `Noto_Sans_SC` from `next/font/google`; replaced its export with a plain object exposing `style.fontFamily` (so `pages/_app.js`'s `--font-sans` binding keeps working unchanged). Kept `Bitter` (small Latin serif) on `next/font`.

**Root cause**: Next 15 changed `next/font/google`'s CJK handling. The fork's `lib/fonts.js` (unchanged across the merge) loads `Noto_Sans_SC({ subsets: ['latin'] })`. On Next 14 this generated **0 woff2 files**. On Next 15 the identical code generates **214 @font-face rules, 106 woff2 references, ~1.15MB across 21 font chunks** — Next 15 self-hosts the full Noto Sans SC family regardless of `subsets`.

This 1.15MB font payload was the primary TBT/Style&Layout regression: each chunk load forced a relayout. Diagnosed by grouping Lighthouse network requests by MIME type (pre-merge: 0 `font/woff2`; post-merge: 21 × ~56KB = 1179KB).

**CJK rendering**: Preserved via the `FONT_SANS` system fallback stack (PingFang SC / Microsoft YaHei / Source Han Sans SC / Noto Sans CJK SC). Browser-verified: article CJK headings/body render correctly, no tofu glyphs.

**Measured impact** (Lighthouse mobile, 3-run median):
| Metric | pre-merge (N14) | post-merge (N15) | after this fix |
|--------|-----------------|------------------|----------------|
| Homepage perf | 91 | 75 | **91** (fully recovered) |
| Homepage TBT | 64ms | 270ms | **172ms** |
| Article TBT | 205ms | 1752ms | **551ms** |
| Article Style&Layout | 1383ms | 3431ms | **1772ms** |

> **Review concerns**:
> 1. Visitors without any CJK system font (rare — most OSes ship one) will see Latin Bitter + a generic sans for CJK. Acceptable trade-off vs. 1.15MB? The fork's prior behavior (pre-Next-15) also relied on system fonts since Next 14 didn't self-host Noto SC.
> 2. Article TBT (551ms) is still ~2.7× the pre-merge 205ms. Residual is Next 15 baseline overhead (framework chunk eval: 358ms→391ms), not font-related. Out of scope for this merge.
